# 踩坑笔记(问题 → 尝试 → 结论)

## 2026-09-13 · Day 15-16

- **GitHub 直连慢且频繁断流** → curl 下载 246KB 数据集断 3 次 → `curl -C -` 断点续传 + 重试循环 3 分钟内补完;HEAD 探测经常被吞,别指望 `-I` 判断大小。
- **Global Superstore 美国拆 4 个 region,country 做主键必撞** → 第一版 geography(country PK)插入报 UNIQUE 冲突 → 改 (country, region) 复合主键,customers 带 country+region 关联;"国家→唯一区域"的直觉在这份数据上不成立。
- **SQLite 没有独立 COMMENT 语法,列注释会丢?** → 不会:DDL 原文(含 `-- 中文注释`)整个存进 sqlite_master.sql,`get_schema` 直接 `SELECT sql FROM sqlite_master` 读回,模型看到的就是带注释的建表语句,零额外元数据表。
- **脏数据注入规则在同一条明细上撞车** → row_id 58 同时命中 quantity=0 / quantity=-2 / sales=NULL 三条规则,5 行预算只脏了 3 行 → 规则改成互相排除已命中行;教训:确定性注入也要断言"victim 不重叠"。
- **Qwen3.8-27B(vLLM)原生 function calling 可用** → 探测脚本确认 tool_calls 正常返回,`enable_thinking: False` 时 content 为空、意图全在 tool_calls 里 → agent 循环用原生协议,不走 JSON 模拟;但要注意"空 content + 无 tool_calls"要和"模型真在说话"区分,前者提醒一次,连续两次才降级。
- **模型第一枪就打偏枚举值(APAC ≠ Asia Pacific)** → 未做约束时它自己查了一遍 market 枚举再改 SQL(5 步完成)→ 错误信息/空结果原样回传就够了,模型的自愈倾向比预想强;Day 17-18 在此基础上做正式的反思与重试上限,并量化开关对比。

## 2026-09-13 · Day 17-18

- **"展示的表格"和"结论"对不上(最隐蔽的一个 bug)** → 现象:问"2013-03 亚太订单数",结论正确说 0,返回表格却是 9 行国家枚举 → 原因:模型最后一步做枚举探查后直接 final_answer,没重跑计数,而表格取"最近一次成功查询" → 修复:final_answer 自报的 SQL 在本地重执行作为权威表格(不耗 LLM 调用),跑不动再回退;教训:agent 的"最后状态"不等于"回答依据的状态",展示层要和结论锚定到同一条 SQL。
- **反思提示在"合法的 0"上也会触发** → "数量>100 的行数"这类问题答案本来就是 0,反思照样注入 → 观察:模型能正确判断"数据本身如此"并如实作答,多花 1 轮但答案更稳 → 保留该行为,提示文案里明确写了 (b) 分支"接受结果如实说明",避免硬找不存在的错误。
- **eval 明细必须存最终表格** → 第一版只存 stats/sql,排查 q19 不匹配时两眼一抹黑 → 记录里补上 columns/rows/gold_rows 各前 20 行,一眼看出是"表格错"还是"压根没查"。

## 2026-09-13 · Day 17-18(评估方法论)

- **gold 里写 ROUND + 判定器再圆整 = 并列陷阱** → 利润率 0.49997 被 ROUND(4) 抬成 0.5,与真 0.5 并列,Top-5 的 gold 变成"6 选 5 非确定" → 原则:**gold SQL 永不圆整,容差只在判定器一处**;浮点比较的精度选择本身就是实验设计。
- **判定器过严会把"答对了"判成"错"** → 模型问"多少客户"返回 (COUNT, COUNT DISTINCT)=(800,800)、问"利润率最低"返回完整排名,值集合比对全判错 → 改成列子集投影 + 单行 gold"答案点包含";教训:评测口径要先看错题明细,分清"模型错"还是"尺子错"(4 道疑错里 3 道是尺子错)。
- **自然跑分测不出自愈价值** → 25 题 × 2 轮,首枪 SQL 报错率为 0(注释 DDL + 强模型),开关对比无差异 → 补**故障注入实验**(--chaos:每题首条 SQL 强制改错表名),0% → 88% 的恢复率才是自愈的真实量化;强模型时代,自愈是鲁棒性保险而非准确率杠杆——这个结论本身就是面试谈资。
- **语义错误是自愈盲区** → q20 问季度答按月、q25 中位数取上中位值,SQL 全都跑通且结果非空,反思提示不触发 → 明确记录边界:自愈覆盖"执行错误/空异常结果",不覆盖"跑通但答非所问";后者的杠杆在提示工程与 schema 信息注入(Day 19)。

## 2026-09-13 · Day 19

- **DDL 注释手写枚举与数据不一致是枚举陷阱的根源** → 排查发现 market 注释写 `APAC / EU`,库里实际是 `Asia Pacific / Europe`;discount 注释 0~0.5 实为 0~0.8;文档声称日期范围 2013-2014 实为 2012-2015 → 修法:低基数码列的枚举、日期覆盖、折扣范围全部由 `build_db.py` 从数据**动态计算**渲染进 DDL 模板,注释↔数据不一致这一类错误从机制上消失;并加回归测试逐值断言"注释包含库中每个实际取值"。
- **信息注入是最便宜的正确率杠杆** → 季度口径示例写进 order_date 注释 + system prompt 后,q20(问季度答按月)一枪修复;q06(枚举陷阱)从 5 步探查降为 1 枪。代价只是每次 get_schema 多几百 token。
- **gold 与题意不符时,模型进步会"伪装成退步"** → q21 题目问"2013 和 2014 两年各自",gold 却不过滤年份(返回 4 年);基线模型没过滤才碰巧对,Day 19 模型正确过滤反而被判 ✗ → 先看错题明细分清"模型错还是尺子错"(Day 17-18 的老教训再次生效),修 gold 后 ✓。
- **"合法的 0"仍会触发反思探查** → q19(2013-03 亚太订单数,真实答案 0)模型探查 3 次确认后如实作答,多花 ~7s 但结论稳 → 保留;反思的 (b) 分支文案是关键,避免硬找不存在的错。

## 2026-09-13 · Day 20

- **深色主题下 Vega-Lite 默认黑字不可读** → 首版 spec 交给 `st.vega_lite_chart` 渲染,Streamlit 深色主题只接管图元配色,标题/轴文字仍是黑字黑底 → spec 固定 `background: white`(图表自带白底),深浅主题都可读;UI 问题必须真开浏览器截图看,DOM 快照里 canvas 内容不可见。
- **图表选型的真实盲区来自模型输出习惯** → 计划里的"两数值列→散点"在真实链路几乎凑不齐:模型对"关系"类问题倾向聚合成分箱表(单维度+多数值→柱),要明细时又爱带上 row_id/order_id(id 列被当维度)或多算比率列(profit_margin_pct/pct)把数值列顶到 3+ → 修法:柱/横条取前两个数值列、饼图只画第一个数值列;散点保留给真正的两数值形态,由单测覆盖确定性。
- **饼图占比口径要与模型自算分开** → 模型常自己带一列 pct(且分母可能是全库合计),图表按"图内合计"重算 share,两边数字会有 46.8% vs 46.72% 式的微差 → 解读明确写"图内合计",不冒充全局占比。
- **NULL 剔除必须双侧一致** → 图表剔除"画不了"的行(维度/数值 NULL)时,剔除行数写进解读("另有 N 行…表格中仍可见"),表格保持全量——只改图不改口径说明,用户会对不上数。

## 2026-09-13 · Day 21

- **并列陷阱在比率题复发** → q22 问"利润率最高的 5 个商品",库里 6 个商品利润率恰好都是 0.5,top-5 无确定答案,模型选谁都是"错"(Day 17-18 的 ROUND 并列换了件马甲:这次不是圆整造出来的并列,是数据本身整比率) → 原则升级:**出 top-N 题前先查边界值多重性**(SELECT 值 + 计数),有并列就换问法或换指标,而不是给 gold 加 tiebreak(模型的 tiebreak 和 gold 永远对不齐)。
- **自愈上限随 schema 质量上移** → 同一注入实验(首条 SQL 改错表名),Day 17-18 恢复率 88%(q19 因枚举探查叠加触 8 步上限),Day 19 枚举入 DDL 后 100%——"错误回传重试"的收益不被无关探查吃步数时才能完全兑现;给自愈算上限时要把步数预算被其他机制挤占的情况算进去。
- **中位数提示要写到"返回形态"** → 第一版只写"偶数个取中间两值的平均",模型确实取到了中间两值,但返回两行不取 AVG;补上"最终只返回一个数值"才一枪修复——口径提示除了算法规格,还要规定输出的形状。
- **token 级白名单的关键在词法分类,不在关键字表** → 正则 `^(select|with)` 时代的焦虑(前导注释/字面量伪装)在把字符串/引号标识符/注释各自切成 token 后自然消失:`SELECT 'DROP TABLE'` 不误杀、`WITH x AS (SELECT 1) DELETE` 拦得住;先 tokenizer 后关键字表,顺序不能反。
- **只读连接挡不住算力攻击** → `mode=ro` 让所有写语句物理失败,但无界 RECURSIVE CTE 能把只读查询跑成资源耗尽 → `set_progress_handler`(虚拟机指令回调 + 单调钟期限)按秒掐断,测试用 `WITH RECURSIVE c(x) AS (... x+1 ...)` 无限递归验证 <3s 中断。

## 2026-09-13 · 外部评审三轮

- **无界状态是进程内缓存器的隐藏雷** → 按 IP 建字典的固定窗口限流,正常流量永远只有几十个键,被伪造来源一打就是无界增长——任何"key 进字典"的设计都要回答"谁负责删";这里用规模阈值 + 锁内惰性清扫过期窗口兜底,规模再大就该换 Redis/网关而不是继续加代码。

## 2026-09-13 · 饼图标签两连坑(Vega-Lite layer 共享比例尺)

- **theta 通道绑原始数值,文字落在扇区终点角而非中点** → 文字层的 theta 直接用销售额字段,角度=该值占合计的比例(=扇区终点),Europe 的标签压进 Asia Pacific 扇区 → 修法:Python 预算扇区中点角 `_mid`(度),文字层 theta 显式 scale [0,360] 按角度定位。
- **layer 之间默认共享比例尺,显式 scale 会反向污染 arc 层** → 上一修法给文字层 theta 设了 [0,360] 值域,Vega-Lite 把它和 arc 层的堆叠 theta 比例尺合并,arc 的堆叠值(0~170 万)被套进 360 度,每个扇区拉成整圈、五个整圈叠成一色 → 修法:`resolve.scale.theta=independent` 让两层各用各的;教训:**在 layer 里给任何通道显式设 scale 前,先想清楚这个通道是不是被别的层共享**。

## 2026-09-13 · 饼图最终修复(显式 theta/theta2)

- **resolve.independent 治不了堆叠污染,别把它当万能开关** → 上一轮加了 resolve.scale.theta=independent 后扇区仍是整环(五个满环叠成一色);隐式 theta 堆叠一旦和"另一层 theta 显式 scale"同场,连 resolve 都拉不回来 → 根治:彻底放弃隐式堆叠,Python 算好每扇区 _start/_end(度),arc 层 theta+theta2 显式绑字段、scale 域 [0,360],与文字层同域,不存在任何可被共享污染的比例尺。
- **"看截图说修好了"不可靠,渲染验证要拿几何数据** → 连续两轮我在截图里"看到"了正常饼图,用户拿 SVG 路径证明扇区仍是整环(每条路径外圈+内圈都是完整圆弧=满环);最终以解析 arc path 的 d 属性计算张角(166.4°/104.2°/46.6°/22.2°/9.5°)对照占比理论值才坐实修复 → 视觉印象会脑补,几何数据不会。
